# Connections & Target

The first module configures both ends of the migration. Every other module reuses them.

## Source

Enter the server host, port, database and login, then **Test source connection**. The
login needs the read-only [source grants](../installation.mdx#source-database-grants).

## Lakebase target

Enter the Lakebase host, port, database, SSL mode and **role**, then **Test Lakebase
connection**. Use a Postgres role with create and insert privileges on the target database.
The **Identifier casing** option (*Preserve source schema and object casing*) switches the
project from lower-cased to source-cased names — see
[Naming on the target](./index.mdx#naming-on-the-target).

### Authentication

- **Password** — a Postgres role name and password, always over TLS.
- **Databricks identity** — connects as you, the signed-in Databricks user, with a
  short-lived OAuth token minted per connection. No password is entered or stored.
  Running locally, the CLI profile is the user.

Databricks identity needs two things:

1. The app's `postgres` user authorization scope (set in `databricks.yml`). Each user
   consents once when they next open the app.
2. A Postgres role for your identity on the Lakebase project. Lakebase creates one
   only for the project owner; anyone else needs the owner to run:

   ```sql
   -- databricks psql --project <project-id>
   CREATE EXTENSION IF NOT EXISTS databricks_auth;
   SELECT databricks_create_role('you@example.com', 'USER');
   ```

   The role also needs create and insert privileges on the target database.

:::note

With Databricks identity, **Job and Async modes run the job as you**: the notebooks mint
your OAuth credential themselves, so no Lakebase secret is written. Setting another user
as a job's *Run as* needs a workspace admin. If the app's service principal isn't one, the
job is created without running (a schedule stays paused) and you get Manage permission on
it. Open it, set **Run as** to yourself, then **Run now**. Keep the app open during a long
**Sync now** run: each new connection mints a credential from your latest sign-in. See
[Limitations](../reference/limitations.mdx#lakebase-authentication).

:::

## Passwords

Each password can be **typed** or taken from a **Databricks secret** (scope and key in the
bound workspace, including Key Vault-backed scopes on Azure). A secret holding a full
connection string fills in the coordinates too.

- Password values are **never saved in the project**. Secret mode saves only the
  workspace/scope/key reference.
- A typed password that tested successfully is remembered by the backend for that project,
  so a page reload does not lose it. With the Lakebase project store it is kept
  **Fernet-encrypted**, with the key in the secret scope — never in clear text. See
  [Persistence](../architecture/persistence.mdx#credentials).

**Save connection** stores the coordinates and secret references on the project.

## When the test fails

- **Timeouts** usually mean no network path: the source firewall needs the app's egress IP
  (set `egress_probe: "true"` to log it), or a private link.
- **Login failures** — check the login and its grants.
- Reproduce the app's exact connection path from a terminal with
  `scripts/azure_sql_connect.py` — see
  [Troubleshooting](../reference/troubleshooting.mdx#testing-the-source-connection).
